## Activation Contract

Load in the main session, on every engine: `gabo-assistant` loads this skill there and runs it with the same inputs; no `gabo-cycle` runs as its own agent, so every coder is a first-level subagent of the main session (spec 0015 S1). In this skill, "return to the assistant" means continue with the assistant's Wave Close in the same session. The assistant gives you a wave id, the mode, the wave start time on a wave start, and `resume <session id>` when it resumes a wave (its own session's, or the holder's from the trace after a restart on the owner's request); you run that one wave and produce the wave report. A wave is exactly one accepted intent: the wave id is the intent id (`I####`), and the wave runs only that intent's tasks. You use the `tasks`, `repository_host` and `memory` slot adapters. The whole wave runs through this skill and those adapters: no `gabo` command and no state dir (D15, D17).

## Hard Rules

- Target `repo.integration_branch` (`dev`); never `main`.
- Launch at most `parallelism` coder subagents at once (`gabo-coder`), one per task, each in its own worktree: `parallelism` bounds the coders in parallel within this intent. Never exceed it while a review runs. When several waves run at once (one per session), `parallelism` bounds this wave only; there is no project-wide counter (spec 0013 open question 3, owner).
- Session engine (intent 0013 S7): you run the wave on the engine of your main-session entry: the `gabo-engine:` line of your built agent file (`{{engine}}`, intent 0013 S6) or the fixed session-engine line of the block. When `runtimes.coder` is `session` or equal to your session engine, coders are in-process subagents as today. When it is another fixed engine, coders still run in-process on the session engine (subagents cannot change engine, TRD 2) and the wave report carries `coders ran on <session engine> (runtimes.coder is <engine>; subagents inherit the session engine)`. The wave report always carries `session engine: <engine>`. An entry with no engine line (an agent file built before the slot, or a block without that line) gives `session engine: unknown (rebuild the agents)`; then a `session` value in `runtimes.coder` or `runtimes.reviewer` cannot be resolved: start no task, claim nothing and return that as the question for the assistant.
- Intent claim (intent 0013 S8, D4): a wave claims its intent before it claims any task, with no new `tasks` operation (D4): only `log progress` and `read one` on the intent issue (the `I####` issue the wave id names). The session id is `<engine>-<8 hex>` (your session engine, `unknown` without an engine line, and eight random lowercase hex digits), made once per wave start and kept in `gabo/trace/<run id>` (the run id `<I####>-<YYYYMMDDTHHMMSSZ>` the assistant passes, one per wave run: it keys the trace, the ledger, the stamps and `--wave`, so no save of one run overwrites another's; the claim, the worktree namespace and `gabo/trace/<I####>/planning` keep the intent id); every return to the assistant (wave report, questions, refusal) ends with the line `session id: <session id>`. The trace is shared by every session of the project, so a session id found there is never adopted on its own: a resume keeps a claim only when the assistant passes `resume <session id>` and that id equals the session id in the trace. A claim is the comment `intent claimed by session <session id> (engine <engine>) run <run id>`; a release is `intent released by session <session id>`, or `intent released by owner for session <session id>` posted by an assistant on the owner's instruction. Taking the comments in the tracker's comment order, not by clock, the earliest claim not followed by its own release holds the intent. A session that does not hold it posts its release, claims nothing, launches no coder and returns only three lines: `intent <I####> is claimed by session <session id> (engine <engine>) since <UTC time>; it is released when that wave closes`, followed by `The owner can release it by telling any assistant to release session <session id>.` (the holder's id, engine and claim comment time), then its own `session id: <session id>` line. The holder keeps its claim on resume, re-checks it with `read one` before each coder launch (step 5), and posts its release at wave close (step 7). There is no timeout: a claim whose session ended without closing its wave holds until that wave is resumed by its own session and closes, or until the owner releases it (spec 0013 open question 1, owner). This includes an orphan claim, one whose session died between its claim and its own release: it may hold once the earlier holder releases, and only the owner's release frees it.
- One intent per wave: never take a task of another intent. A task of this intent blocked by a task of another intent stays blocked: it is reported, never pulled in, and that other task is not started.
- Reviewer isolation gate: a wave, auto mode included, never starts with a `codex` or `opencode` reviewer that has no isolation test pass (intent 0002 S12): when `runtimes.reviewer` in `gabo.yaml` is `codex` or `opencode`, run the reviewer preflight (step 1) before you claim any task. On failure start no task, claim nothing and launch no coder. There is no other way around the check: the only fix is the owner running the `gabo-reviewer-config` isolation test at configuration time, never during a wave. `claude` and `pi` reviewers start as before, without this step. Under `runtimes.reviewer` `session`, resolve the review engine first and apply the same gate to the resolved engine (step 1, intent 0013 S11).
- Launch only coders: while the main session runs the cycle it launches `gabo-coder` subagents and no other agent (no explorer, verifier or reviewer: the coder runs the reviewer script itself), at most `parallelism` at once and one per task worktree. Reason (a) parallel units: each coder launch is reason (a); a wave of one task launches one coder, because the task is a separate unit in its own worktree. Rule: the launch input starts with `Reason: (a) parallel units`; a resume of a coder by its ledger handle and a replacement coder for the same task continue the unit launched under (a): neither is a new handoff, and both messages repeat the line `Reason: (a) parallel units`. The cycle keeps the first handoff line `Reason: <label>` of each coder in the trace as one line `reason <task id> <label>` (appended with its `session started` line) and the report carries it (`gabo-wave-report` Tasks section).
- Launch coders so that each coder is one first-level in-process subagent of the main session, and its handle goes to the ledger; never a named teammate in its own pane unless the owner asks. Between coders the session ends its turn and never polls: the runtime delivers each finished coder's outcome to this session and wakes it, and each wake is the next outcome of step 6, so the wave goes on to the next task within `parallelism` and to the wave close (step 7). The trace is written after every state change, so a compacted or restarted main session resumes the wave from the tracker, the ledger and the trace, without asking the owner to repeat anything.
- Resource ledger (D15, D23): every worktree, branch, container or test database a coder reports, and the runtime handle that resumes the coder, go into `gabo/ledger/<run id>` through the `memory` slot as soon as they are known. One line per resource: kind, name or path, creator, task, the session id of this wave, state (live, removed, leftover). The ledger holds only this wave's resources (intent 0013 S9).
- Worktree namespace (intent 0013 S9, D6): every worktree of this wave lives under `<repo-parent>/<repo-name>-worktrees/<wave>/`, one per task at `<repo-parent>/<repo-name>-worktrees/<wave>/<task>`, where `<repo-parent>` is the parent directory of the main checkout's root, `<repo-name>` that root's directory name and `<task>` the task id (`T###`). Another wave's folder is never yours.
- The coder owns its task close and is the only writer of DONE (D23); the cycle never writes DONE. A coder that gets `merge=merged` closes on its own; after any other merge the assistant resumes it by the handle you recorded. A coder without a handle, or one the runtime cannot resume, is replaced: on a resume the holder launches a new `gabo-coder` for it (step 3), so a coder always closes the task and this session never does.
- Your own cleanup (fallback sweep) runs only from the ledger: it touches only entries of this wave's ledger (`gabo/ledger/<run id>`), only for entries no coder could close, only after `repository_host` shows the PR merged, never removes the worktree or the branch of a task that is neither DONE nor BLOCKED, even when its PR is merged (its issue is open and a coder can still close it, step 3), so it takes an entry only after its task is DONE or BLOCKED; a BLOCKED task's issue stays open, and its entries are swept only when its PR is merged, as before, with ordinary commands and no `gabo` command: `git worktree remove <path>` (never `--force`), branches through `repository_host` (delete branch), `docker rm` for ledger containers, the database's own drop command for ledger test databases. Skip `worktree.keep` entries. A removal that fails is REFUSED: leave it and list it under leftovers. Never delete anything outside this wave's ledger. A resource of another wave (an entry of another `gabo/ledger/<run id>`, a worktree under another `<repo-name>-worktrees/<wave>/` folder, or a branch, container or test database another wave's ledger names) is neither removed nor reported as a leftover of this wave. Any other resource you find that is in no ledger is reported as found, never removed and never listed as this wave's leftover.
- Operating rules (PRD 8.1, TRD 9.5):
  - rule 1: a mid-wave task change waits for the round in progress. Re-read the task through `tasks` before each coder round (launch, fix round, resume) and pass the current text; never interrupt a round.
  - rule 2: during a plan-change debate mark only the affected task BLOCKED; the rest of the wave continues.
  - rule 3: a coder that reports BLOCKED after 4 fix rounds leaves its task BLOCKED; its question goes to the wave report for the assistant. Never launch a fifth round.
- Every write is re-read (R24): tracker writes through `tasks`, ledger and trace writes through `memory`. A write whose re-read does not show it is retried once, then listed under Unverified writes in the report.
- Board or tracker moves are never skipped silently: a denied write is returned as the exact list (`issue -> Ready`, `issue -> Backlog`) for the assistant to apply.
- Wave caps (intent 0020, all optional, unset means no cap and every rule above and below is unchanged): the counters live in `gabo/trace/<run id>` (D17): coders launched this wave, fix rounds per task and turn-stopped coders.
  - `wave.max_coders`: launch no more than that many coders in the wave in total, counted from the wave start or from the last `cap max_coders reset` line of the trace (a "continue" by the owner starts a new count, PD9). a resume of a coder by its ledger handle does not count; every other launch counts, and a replacement `gabo-coder` counts. The cycle pauses before a launch that would exceed it.
  - `wave.max_fix_rounds`: with it below 4, pause when a task reaches that many fix rounds without a clean review; the task is not BLOCKED. The launch input to `gabo-coder` carries `fix round limit: <n>` on every engine when `wave.max_fix_rounds` is set below 4, in the same place and with the same wording pattern as `turn limit: <n>`; with it unset or 4, rule 3 is unchanged and no `fix round limit` is passed ("Never launch a fifth round" stays). A coder that returns `STOPPED at fix round limit` counts as stopped at the cap `max_fix_rounds`: its task stays claimed with its ledger handle and nothing is written BLOCKED or DONE; the wave pauses with the cap `max_fix_rounds`. Exception (intent 0024 S6): when that coder reports a head SHA, re-read the review of the head SHA it reports; if the verdict is clean on that head, the task is not stopped at the cap: the task is handled as HANDED (the coder, never the cycle, writes DONE, D23): the coder runs Task Close after `verdict=clean merge=merged`, or when resumed by its ledger handle (or a replacement coder, step 3) with `PR #<n> merged`; it finishes through Task Close (the normal DONE path) and the wave does not pause, and the task's line in the report says `finished at the fix round limit (clean head)`; with a blocking review the wave pauses with the cap `max_fix_rounds` as before.
  - `wave.max_coder_turns`: the launch input to `gabo-coder` carries `turn limit: <n>` on every engine. With `wave.max_coder_turns` set only (unset keeps today's handling of a coder without a status), a coder that returns without an outcome status (`HANDED`, `DONE` or `BLOCKED`), that is, partial output (Claude Code), no outcome status after a wrap-up summary (OpenCode) or `STOPPED at turn limit` (the advisory engines, Codex and Pi) counts as stopped at the turn cap: its task stays claimed with its ledger handle and nothing is written BLOCKED or DONE; the wave pauses with the cap `max_coder_turns`.
  - A pause launches nothing new and lets the running coders return (each outcome wakes this session as in step 6). It saves the state in the tracker, the ledger and the trace and ends with the paused report of `gabo-wave-report` for the assistant, whose cap lines are the output of `sh .gabo/skills/gabo-wave-report/scripts/wave-record.sh caps --engine <engine> --paused` (`<engine>` is the session engine only when the built `gabo-coder` agent of that engine holds the turn key its runtime skill names (`maxTurns:` for Claude Code, `steps:` for OpenCode), and `--engine none` otherwise) pasted unchanged (the cycle returns its output in the paused report), with `session id: <session id>`; it keeps the intent claim. A task claimed in step 4 whose coder a pause kept from launching stays claimed with no worktree and no PR; on resume the cycle launches it as a first launch (step 5), counted against `wave.max_coders`. Merge, review and `review.auto_merge` behavior is untouched by a cap.
  - On resume after "continue" (the assistant's `resume <session id>`), append one trace line `cap <name> reset <UTC time>` and the cycle counts that cap from zero. For `max_fix_rounds` (trace line `cap max_fix_rounds reset <UTC time>`) the allowance restarts but the 4-round ceiling stays absolute for the task: a coder resumed by its handle or a replacement coder gets `fix rounds used: <k>` (the rounds the task already took, from the PR's review rounds) and `fix round limit: <k + wave.max_fix_rounds, never above 4>`, so the limit counts total rounds and the restarted allowance is the difference; at 4 total rounds rule 3 applies (BLOCKED, never a fifth). A turn-stopped coder keeps its claim: the cycle resumes the coder by that handle (not counted), or, when the handle cannot be resumed, launches a new `gabo-coder` on the ledger worktree and branch as in step 3; that replacement counts against `wave.max_coders` and the cycle pauses before it if the cap is reached.
- Trace (D17): after every state change append the task's status, PR, last verdict, fix rounds and open questions to `gabo/trace/<run id>`, enough to resume. Also append, never reset by a "continue" (unlike the cap counters), `session started <agent> <task id> <UTC time>` for every agent session it starts (a replacement coder included; a resume by a coder's ledger handle starts none) and one line per PR it sees opened and one per PR it sees merged. The report's measures are built by `gabo-wave-report` from these lines. Every session the cycle starts gets `sh .gabo/skills/gabo-wave-report/scripts/wave-record.sh --wave <run id> stamp session-started <agent> <task id>` (step 5, a replacement coder of step 3 or of the turn-cap resume included, none for a resume by a coder's handle). At the report step the trace adds the content of the stamps file (`${XDG_STATE_HOME:-$HOME/.local/state}/gabo/waves/<run id>/stamps`) as one more entry of `gabo/trace/<run id>`, never replacing the entries above (session id, wave start, task states), and the cycle runs `sh .gabo/skills/gabo-wave-report/scripts/wave-record.sh --wave <run id> saves add '<topic key>#<entry>' <observation id>` after every memory write of the wave and `sh .gabo/skills/gabo-wave-report/scripts/wave-record.sh --wave <run id> saves read '<topic key>#<entry>'` after each read-back whose observation shows that entry's text, and pastes each output unchanged. The entry is the label of the line written: `start` for the wave start entry, the task id for a task's line, `stamps` for the stamps entry and `report` for the report entry of `gabo/trace/<run id>`, and `ledger` for each ledger entry of `gabo/ledger/<run id>`; the observation id is the one `mem_save` or `mem_update` returned, so two entries of one observation are two ledger entries and `saves unverified` lists each one not read back (the wave start entry calls of step 2 included). If the script is missing or exits non-zero, report `unverified: wave-record <subcommand> failed (<reason>)`, continue the wave and never write the line the script would print. Also, the trace saves are mandatory: the wave start entry, one entry per task and the wave report as the last entry; each is read back before the final answer, and a save that does not show up after one retry is listed as unverified in the report.

## Execution Steps

1. Reviewer preflight, only when `runtimes.reviewer` is `codex` or `opencode`, auto mode included: run the user-level copy, never a copy from a repository checkout, with no extra arguments or environment: `bash "${XDG_DATA_HOME:-$HOME/.local/share}/gabo/skills/gabo-reviewer/scripts/reviewer.sh" preflight`. It reads the isolation pass marker of the engine and its installed version (intent 0002 T2). `PREFLIGHT-OK` ⇒ continue. Any other result (a `PREFLIGHT-FAILED` line, a non-zero exit, or a missing script) ⇒ start no task, claim nothing, launch or resume no coder, and return the wave report with the `PREFLIGHT-FAILED` line verbatim, which names the missing isolation test, as the question for the assistant.
   With `runtimes.reviewer` `session`, resolve the review engine first: `runtimes.reviewer` `session` is your session engine; a fixed `runtimes.reviewer` is that engine and keeps the step above unchanged. When the resolved engine is `codex` or `opencode`, run the same user-level copy with `engine <engine>` appended as its only extra argument, only under `session`: `bash "${XDG_DATA_HOME:-$HOME/.local/share}/gabo/skills/gabo-reviewer/scripts/reviewer.sh" preflight engine <engine>`, still before any claim, with the same outcomes. A resolved `claude` or `pi` engine starts as before.
2. Intent claim (Hard Rules), after the preflight and before any resume or task claim. Only when the assistant passes `resume <session id>`, read the session id from `gabo/trace/<run id>` and `read one` the intent issue: if the passed id equals the session id in the trace and still holds the intent, keep it and post nothing (it keeps its claim on resume); otherwise continue as a wave start with the current time as the wave start time and a new run id built from it as `<I####>-<YYYYMMDDTHHMMSSZ>`, never adopting the trace's session id or the passed run id; in that case the cycle builds the run id itself and returns it to the assistant on a `run id: <run id>` line just before the `session id:` line, and the assistant uses it from then on. Wave start: make the session id (the run id comes from the assistant, or is the new one above), post `intent claimed by session <session id> (engine <engine>) run <run id>` on the intent issue through `log progress`, then `read one` it (verified). The holder by the rule is you ⇒ save the session id and the wave start time in `gabo/trace/<run id>` with `save wave trace` through `memory` (verified) and continue; every entry of this wave is a line of that one trace observation, extended with `save wave trace` (search the key, then `mem_update`, else `mem_save`), never a second observation; a refused session writes nothing to the trace. On a wave start only (never when the holder resumes), run `sh .gabo/skills/gabo-wave-report/scripts/wave-record.sh --wave <run id> stamp wave-started` and `sh .gabo/skills/gabo-wave-report/scripts/wave-record.sh --wave <run id> stamp session-started gabo-assistant main` (the main session) and paste each output unchanged; the stamps are kept per run id, so a new start never finds an earlier run's stamps (when the script is missing or exits non-zero, report `unverified: wave-record <subcommand> failed (<reason>)`, continue the wave and never write the line the script would print). Another session holds it ⇒ post `intent released by session <session id>` with your own id through `log progress`, read it back, and return the refusal line and the owner-release sentence; claim nothing. The wave start entry save is followed by `sh .gabo/skills/gabo-wave-report/scripts/wave-record.sh --wave <run id> saves add <topic key> <observation id>` and, after its read-back matched, `sh .gabo/skills/gabo-wave-report/scripts/wave-record.sh --wave <run id> saves read <topic key>`, the same as the report entry.
3. Resume (D17), only as the holder: read `gabo/trace/<run id>` and `gabo/ledger/<run id>`, then re-read every wave task through `tasks`, and recompute the wave from tracker state plus that ledger and trace. The cycle skips DONE tasks (closed issues). An open PR (`repository_host` read status) or a live ledger worktree ⇒ reattach: resume its coder by its handle, or launch a new coder on that worktree and branch. When a coder handle that cannot be resumed (no transcript after a session close or restart) is the only way to reach an open task, launch a new `gabo-coder` on the ledger worktree and branch with the same input as a first launch (task, worktree path, branch, mode), stamped as in the Trace rule, with `PR #<n> merged` when `repository_host` shows the PR merged; when the PR is `CONFLICTING`, with the instruction to run the coder's `CONFLICTING` fix round (merge `origin/dev` into the task branch, never a rebase, never a force-push, resolve the conflict, run the task's checks, push, request a new review); otherwise with the PR number and the instruction to read the PR status and the latest reviewer comment and continue from them, as a fix round after a blocking verdict or as a hand-off after a clean one. When the worktree or the branch is already gone and the PR is merged, the new coder runs the Task Close from the main checkout (verify the merge through `repository_host`, close the issue with DONE via PR; nothing else to remove); it cannot derive the main checkout from a worktree that is gone, so give it the main checkout path (your own working directory) in its input. When the worktree is gone and the PR is still open, the new coder recreates it in the main checkout with `git worktree add <worktree path> <branch>` (from `origin/<branch>`) and continues, or returns the question when the branch is gone too. The new coder is the only writer of DONE. When tracker, host and trace disagree (for example the trace says HANDED and the issue has no PR), record the disagreement in the report and leave that task alone; never guess.
4. Read this intent's tasks through the `tasks` adapter: `read unblocked` with the `intent` filter set to the wave id (every one of their blocked-by links counts, a blocker in another intent included); take up to `parallelism`. Claim each (verified). Tasks of this intent whose blocker belongs to another open intent go to the wave report as blocked across intents.
5. Per task: re-read it (rule 1) and `read one` the intent issue: when you no longer hold the intent (an owner release), launch no more coders and return the wave report with that as the question for the assistant; `git worktree add <repo-parent>/<repo-name>-worktrees/<wave>/<task> -b <branch> origin/dev` (Worktree namespace), record worktree and branch in the ledger with your session id. On Pi (your session engine is `pi`), register that worktree before the coder launch: call `session_worktree_register` on its path and, when it returns success, add `registered` to that worktree's ledger line. When the tool is missing or the call fails, launch the coder anyway, add `worktree not registered (<reason>)` to that ledger line and to the wave report, and never stop the wave for it. On another engine register nothing. Then, before the launch call, append `session started <agent> <task id> <UTC time>` to `gabo/trace/<run id>` yourself (a coder resumed by its handle appends none), run `sh .gabo/skills/gabo-wave-report/scripts/wave-record.sh --wave <run id> stamp session-started <agent> <task id>` before the launch call and paste its output unchanged (a coder resumed by its handle runs none), and launch `gabo-coder` as a first-level in-process subagent of this session (on your session engine) with `Reason: (a) parallel units` as its first line, then wave id, task, worktree, branch and mode (and `turn limit: <n>` when `wave.max_coder_turns` is set, and `fix round limit: <n>` when `wave.max_fix_rounds` is set, Wave caps); record its handle; with `wave.max_coders` set, pause first when this launch would exceed it. Each coder's `session started <agent> <task id> <UTC time>` line is saved to the trace in the same step as its `stamp session-started`, so a trace read back shows one such line per coder.
6. On each outcome (HANDED, DONE, BLOCKED): append its resources to the ledger; update the task (BLOCKED status, PR link; never DONE) and the trace; in the same step, append the PR line yourself for each PR you see opened and for each PR you see merged, and run `sh .gabo/skills/gabo-wave-report/scripts/wave-record.sh --wave <run id> stamp pr-opened <pr>` for the first and `sh .gabo/skills/gabo-wave-report/scripts/wave-record.sh --wave <run id> stamp pr-merged <pr>` for the second; paste its output unchanged each time; apply rules 2 and 3 and the wave caps (a coder stopped at the turn cap, a coder stopped at the fix round limit); recompute what is unblocked with the same `intent` filter and launch the next task within `parallelism`.
7. The wave closes when every task of that intent is DONE or BLOCKED (blocked across intents included). The one exception is a paused wave the owner stops (`gabo-assistant` Wave Close): it closes with its unfinished tasks left as they are, claimed and with their ledger entries live, and no new coder. Wave close is a fallback sweep: clean the merged entries of this wave's ledger no coder closed (rules above), and skip the entries of a task that is neither DONE nor BLOCKED, without writing DONE; mark every ledger entry removed, live or leftover. Then post `intent released by session <session id>` on the intent issue through `log progress` and `read one` it (verified), so the next claim succeeds.
8. Report: run `sh .gabo/skills/gabo-wave-report/scripts/wave-record.sh --wave <run id> stamp wave-reported`, paste its output unchanged, read `.gabo/skills/gabo-wave-report/SKILL.md` first and build the wave report from it (the TRD 9.2 wave report), save the wave report as the last entry of `gabo/trace/<run id>` through `memory` (verified), then return it to the assistant. Measures is an ordered checklist of eight lines, built line by line from the trace and the tracker: wall time; fix rounds per task; agent sessions; PRs opened and merged; the proposal count; interactions; tokens; each task's outcome; each line is printed even when it reads `unknown (<source that lacked it>)`. Before you return it, read the saved wave report back with `read wave trace` and compare it before the final answer, never after it. The entry saved to `gabo/trace/<run id>` at the report step holds the whole output of `cat` of the stamps file exactly as `wave-record.sh` printed it, never a summary or a rewrite, and the report is not returned before that entry is saved and read back.

## Output Contract

The wave report (TRD 9.2) in the format of `gabo-wave-report`, with its comfort answer `pending`, and the save as `verified` or `unverified`. A wave that does not hold its intent returns only the refusal line, the owner-release sentence and its `session id: <session id>` line (step 2); every other return also ends with that line. A wave that returns with HANDED tasks says that it keeps its intent claim and that the claim ends with the wave close or the owner's release.
