# Engine compatibility and integrations

Status for gabo 0.2.10 (tag `apps/cli/v0.2.10`), checked against the code. **Yes** means it ships in 0.2.10; **planned** means it is designed or tracked but does not work yet. The [README](../README.md#compatibility) has the short version.

## Tiers

- **Full**: Claude Code, Codex, Pi and OpenCode. Each has a runtime skill, a plugin or package with hooks, the project-level integration that `gabo init` sets up, and, for Claude Code, Codex and Pi, the engine files that `gabo check` reads.
- **Flexible**: any other engine with subagents and skills. It gets only the gabo skills and configuration: no plugin and no hooks. `gabo init` writes nothing engine-specific for it and prints one line, `<engine>: flexible tier: skills and configuration only; nothing written`, and `gabo check` stays engine-neutral. In 0.2.10, `gabo.yaml` does not accept such an engine name yet (see [Accepted engine names](#notes)).

|---|---|---|---|---|---|---|---|---|---|---|---|
| Claude Code | full | yes | yes | yes | `gabo-runtime-claude` | yes: plugin `gabo@gabo-ai` ([Claude Code plugin](#claude-code-plugin)) | built in | yes, in the plugin | yes, in the plugin | `.claude/settings.json`: `extraKnownMarketplaces."gabo-ai"`, `enabledPlugins."gabo@gabo-ai"`, and `agent` when `runtimes.assistant` lists `claude` | the same keys |
| Codex | full | yes | yes | yes, after the one-time isolation test | `gabo-runtime-codex` | yes: plugin `gabo@gabo-ai` ([Codex plugin](#codex-plugin)) | built in | yes, in the plugin | yes, in the plugin | `.codex/config.toml`: `[marketplaces.gabo-ai]`, `[plugins."gabo@gabo-ai"]` | the same keys |
| Pi | full | yes | yes | yes | `gabo-runtime-pi` | yes: package `@gabo-ai/pi`, `pi install npm:@gabo-ai/pi@<version>` ([Pi package](#pi-package)) | **required**: a subagent package such as gentle-pi; gabo refuses without one | no | yes, in the package extension | `.pi/settings.json`: the `packages` entry `npm:@gabo-ai/pi@<version>` (release builds only) | that entry, any version |

## Notes

- **Accepted engine names.** `gabo.yaml` and `gabo check` accept `claude`, `codex`, `pi` and `opencode` in `runtimes.coder`, `runtimes.assistant` and `runtimes.reviewer`. `runtimes.assistant` also accepts a list of them without duplicates, such as `[claude, pi]`, and `runtimes.coder` and `runtimes.reviewer` also accept `session`, the engine of the main session that starts the wave; a single value keeps its meaning. `gabo check` fails an empty list, a duplicate, an unknown engine in the list and `session` in `runtimes.assistant`, each with a `✗` line naming `runtimes.assistant`, and fails `session` in `runtimes.coder` or `runtimes.reviewer` while `runtimes.assistant` is unset with `"session" is valid only with runtimes.assistant set; next: set runtimes.assistant or name an engine for runtimes.coder` (or `runtimes.reviewer`). Any other value fails `gabo check`, so a flexible-tier engine, including a runtime skill that `gabo-runtime-builder` writes for it, cannot be used until [I0005 (#176)](https://github.com/testeos-z/gabo-ai/issues/176) opens `runtimes.*`.
- **Engine set.** The engines of a project are every engine listed in `runtimes.assistant` plus `runtimes.coder` and `runtimes.reviewer` when each names an engine; `session` adds none. `gabo init`, `gabo check` and the reviewer scripts use this one set: `assistant: [claude, pi]`, `coder: session` and `reviewer: opencode` give claude, pi and opencode.
- **Engine integration by `gabo init`.** For each engine of the engine set, `gabo init` writes the project-level keys of the matrix above, never your global engine config. It only adds missing keys and keeps every value you set, with one exception: it removes the `"gabo-assistant"` main-session key of an engine that `runtimes.assistant` does not list, with the line `removed <file> <key>: "gabo-assistant" (runtimes.assistant is <engines joined with ", ">)`; a listed engine's key is never removed. It ends with an `engine integration:` report that names each file it wrote and what you still need to run, such as trusting the project folder in the engine. Without a `gabo.yaml` it writes no engine file and asks you to run `gabo init` again once your agent has written it.
- **gabo-ai dogfoods `gabo init`.** This repository runs `gabo init` on itself and commits the engine file it writes for its own `gabo.yaml` `runtimes` (all `claude`): [`.claude/settings.json`](../.claude/settings.json) with `extraKnownMarketplaces."gabo-ai"` (the GitHub source `testeos-z/gabo-ai`) and `enabledPlugins."gabo@gabo-ai": true`, so its own `gabo check` verifies those keys.
- **Skill directories (since 0.2.8).** Codex, OpenCode and Pi share `.agents/skills`: one link per name, the same target for every engine, so one set of links serves all three. Claude Code keeps `.claude/skills`, its own folder of links straight to `.gabo/skills`. When `claude` and `opencode` are both declared, OpenCode finds each gabo skill in both folders with the same target; gabo agents read skills by path, so this changes nothing and `gabo check` does not fail on it. A rebuild with `gabo-runtime-pi` or `gabo-runtime-opencode` removes the `gabo-*` links they made earlier in `.pi/skills` or `.opencode/skills` and keeps your own entries; `gabo check` fails on such a link left behind (`✗ <path>: gabo link left after the move to .agents/skills`).
- **Per-agent checks (since 0.2.8; stricter in 0.2.10).** For every engine of the engine set, `gabo check` reads each agent file where its runtime skill says the skill list and the agent's name are (`metadata.agent_skills`, `metadata.agent_name`): the skill list must be exactly the agent's spec skills plus its fixed-name links (`skill <name> missing` / `skill <name> not in the agent spec`; a spec skill or fixed-name link listed more than once, including a link listed under both its link name and its adapter's name, gets one `skill <name> listed twice` line per name instead, after the `missing` lines and before the `not in the agent spec` ones), and a declared name must equal the spec id (`declares name <name>`); a file that declares no name (absent, blank, not a string, or in a frontmatter or TOML that does not parse) fails with `declares no name`, and both name checks also cover the main-session agent file `gabo-assistant` (OpenCode declares no name, so it gets no name check). Every agent file needs a `gabo-version: x.y.z` line, and without a valid stamp the versions are reported as not compared, never skipped. A `gabo-reviewer` skill in a project skill directory or an agent's skill list fails; `gabo-reviewer-config` does not. A flexible-tier runtime skill without `metadata.agent_skills` gets one warning instead of these checks. Each agent file also carries `gabo-engine: <engine>`, the engine it was built for, so an agent knows its session engine; a file in another engine's agent directory fails with `✗ <file>: built for <value>, not <engine>` and `next: ask your agent to rebuild the agents, then rerun gabo check`. A file with no engine line, built before that line existed, passes this check; rebuild it before you use `session`.
- **Agent tools (since 0.2.10).** When a runtime skill declares where an agent file lists its tools and the tools each spec capability requires (`metadata.agent_tools`, `metadata.agent_tool_requirements`; only `gabo-runtime-pi` today), `gabo check` fails each built agent that lacks a required tool with `✗ <agent file>: tools missing for its spec capabilities: <names>` and `next: ask your agent to rebuild the agents, then rerun gabo check`; a required `mem_<x>` is also met by `mcp__<server>__mem_<x>` or `mcp__<server>__*`. An engine without the declaration is not checked, and a Pi agent built before the memory tools were listed fails until rebuilt. When a runtime skill also declares the tools a subagent never has (`metadata.agent_tools_unavailable`; only `gabo-runtime-pi` today, `subagent_*`, a trailing `*` matching a prefix), `gabo check` fails each built agent file that lists one with `✗ <agent file>: tools a subagent never has: <names in file order>` and the same `next:` line. Every `.pi/agents` file runs as a gentle-pi subagent, which never has a `subagent_*` tool, so a Pi agent built before this rule that lists one fails until rebuilt; other engines' output is unchanged.
- **Main-session entry (since 0.2.8).** Your own interactive session runs as the gabo assistant; coder and reviewer sessions keep their role. Every engine listed in `runtimes.assistant` gets its own entry and none removes another. `gabo init` writes the config key of the entry (`agent`, `default_agent`) for each listed engine and removes the `"gabo-assistant"` key of every engine that is not listed. The runtime skill of each listed engine builds the rest on every agent build, the agent file, the skill link and, for Codex and Pi, the block, and removes the agent files, links and blocks of every full-tier engine that is not listed; a shared link or block stays while any listed engine uses it, so rebuilding the listed engines in any order leaves every entry in place:

  | engine | assistant skill link | main-session entry | role sessions |
  |---|---|---|---|
  | Claude Code | `.claude/skills/gabo-assistant` | agent file `.claude/agents/gabo-assistant.md` and `agent: "gabo-assistant"` in `.claude/settings.json` | `claude --agent <id>` overrides the setting |
  | OpenCode | `.agents/skills/gabo-assistant` | agent file `.opencode/agents/gabo-assistant.md` (`mode: primary`) and `default_agent: "gabo-assistant"` in the project config file | `opencode run --agent <id>` picks the role |
  | Codex | `.agents/skills/gabo-assistant` | a scoped block between `<!-- GABO_ASSISTANT_START -->` and `<!-- GABO_ASSISTANT_END -->` in `AGENTS.override.md`, else `AGENTS.md` (created when neither exists) | the block tells a role-prompt or `codex exec` session to ignore it |
  | Pi | `.agents/skills/gabo-assistant` | the same block in the first existing of `AGENTS.override.md`, `AGENTS.md`, `CLAUDE.md` (Pi 1.4.0 loads only that one file per directory; `AGENTS.md` created when none exists) | the block tells a role-prompt or `pi --print` session to ignore it |

  Only that one key or the block is written; every other byte of the file stays, comments included. A key holding another value is yours and kept (`kept <file> <key>: <value> (your setting; gabo leaves it)`). For a flexible-tier engine the key stays with the runtime skill that `gabo-runtime-builder` made, because `gabo init` sets nothing engine-specific for that tier. The Claude Code agent carries a short assistant prompt because Claude Code 2.1.302 does not preload a main-session agent's skills. `gabo check` fails on a missing, incomplete or duplicated entry (`✗ <file>: gabo assistant entry missing for <engine>`, or `incomplete`) and on an entry left for a full-tier engine that is not listed (`✗ <file>: gabo assistant entry for <engine>, but runtimes.assistant is <engines joined with ", ">`, for example `✗ opencode.json: gabo assistant entry for opencode, but runtimes.assistant is claude, pi`). Each line names its fix:

  | piece | `next:` hint |
  |---|---|
  | config key missing (full tier) | `run gabo init (it merges "<key>": "gabo-assistant" into <file>), then rerun gabo check` |
  | config key holding another value (`✗ <file>: <key> is "<value>", not "gabo-assistant"`) | `change <key> to "gabo-assistant" in <file>, or remove it and run gabo init, then rerun gabo check` |
  | config key left for another engine (full tier) | `run gabo init (it removes "<key>": "gabo-assistant" from <file>), then rerun gabo check` |
  | agent file, skill link or block; any piece of a flexible-tier engine | `ask your agent to rebuild the agents, then rerun gabo check` |

  Codex and Pi listed together share one block in `AGENTS.override.md`, else `AGENTS.md`; neither build removes it while the other is listed. Its opening scope paragraph carries one fixed line, ``Session engine: loaded by Codex, this session's engine is `codex`; loaded by Pi, it is `pi`.``, which is how a Codex or Pi main session reads its engine; Claude Code and OpenCode read it from the `gabo-engine:` line of their agent file. A main session that finds neither refuses to name its engine or start a wave with `session engine unknown (rebuild the agents)`.

  After you change `runtimes.assistant`, run `gabo init`, then rebuild the agents of every engine of the engine set. In gabo-ai itself the owner commits the Claude Code entry, because `.claude/` is human-only.
- **Reviewer configuration.** The catalog skill `gabo-reviewer-config` configures any of the four engines as reviewer, or `session`. For `codex` and `opencode` it runs a one-time isolation test first, and under `session` once for each listed `codex` or `opencode` engine; the reviewer runs those engines only while its pass marker matches the installed engine version. A fixed `runtimes.reviewer`, such as `pi`, reviews the waves of every engine; with `session` each wave is reviewed on its own session engine, which the scripts accept only when `runtimes.reviewer` on the integration branch is `session` and that engine is listed in `runtimes.assistant` there.
- **Several sessions in one project.** With `runtimes.assistant: [claude, pi]`, a main session on each listed engine can run a wave at the same time, each on its own intent. A wave claims its intent on the intent issue (`intent claimed by session <session id> (engine <engine>)`) before any task, and the assistant starts waves only on unclaimed intents. Another session asked for that intent claims nothing and returns `intent <I####> is claimed by session <session id> (engine <engine>) since <UTC time>; it is released when that wave closes` and `The owner can release it by telling any assistant to release session <session id>.` A claim has no timeout. Each wave keeps its own ledger (`gabo/ledger/<wave>`) and worktrees under `<repo-parent>/<repo-name>-worktrees/<wave>/<task>`, and cleans only its own resources; list a worktree you want kept by its absolute path in `worktree.keep`, since task ids repeat across waves. Coders run in-process on the session engine; with a fixed `runtimes.coder` that differs, the wave report says `coders ran on <session engine> (runtimes.coder is <engine>; subagents inherit the session engine)`.
- **Pi needs a subagent package.** Pi core has no subagents. `gabo-runtime-pi` builds nothing until a subagent package is present. It recommends [gentle-pi](https://www.npmjs.com/package/gentle-pi) and, as the full setup, the [Gentle AI framework](https://github.com/Gentleman-Programming/gentle-ai) installed with `gentle-ai install --agent pi`. The gabo Pi package is not a subagent package. See [Your engine](setup-prompt.md#your-engine).
- **Tracking.** All engine work is tracked under the product card [#171 Runtime integrations](https://github.com/testeos-z/gabo-ai/issues/171).

## Claude Code plugin

The repository is its own Claude Code marketplace, `gabo-ai`, with one plugin, `gabo`. The plugin adds the gabo catalog skills (except the skills that run reviews) and two hooks that run `gabo check` around Claude's writes in a gabo project.

**With `gabo init`.** When `gabo.yaml` names `claude` in `runtimes.*`, `gabo init` adds `extraKnownMarketplaces."gabo-ai"` and `enabledPlugins."gabo@gabo-ai"` (and `agent`, when `runtimes.assistant` lists `claude`) to the project's `.claude/settings.json`, never to your global Claude Code settings. Its `engine integration:` report then asks you to trust the project folder in Claude Code, so the marketplace and the plugin apply. Commit `.claude/settings.json`. As the alternative, install the plugin at user level by hand:

```sh
claude plugin marketplace add testeos-z/gabo-ai
claude plugin install gabo@gabo-ai
```

- **The `checks` option.** On by default. Before Claude writes or edits a gabo file (`gabo.yaml`, `.gabo/`, `.claude/agents/`, `.claude/skills/`, `docs/product/`), `gabo check --pre-write` blocks a write that breaks the stage gate; after it, `gabo check` runs and reports failures to Claude. Both hooks do nothing outside a gabo project (no `.gabo/VERSION`) or when `gabo` is not on `PATH`. Turn them off with the plugin's `checks` row in `/config`.
- **`gabo init` stays required.** The plugin does not configure a project and ships no agents; `gabo init` writes only the keys above. Per-project config (`gabo.yaml`), slots, adapters and agents still come from `gabo init` and the setup prompt. Inside a project, the copy in `.gabo/skills/` stays the source of truth: the agents preload it and `gabo check` checks it.
- **Skill names.** Plugin skills appear namespaced as `gabo:<name>`, for example `gabo:gabo-pm`, so they never clash with the project copy. To use only the project copy in one project, disable the plugin there with `"enabledPlugins": { "gabo@gabo-ai": false }` in that project's `.claude/settings.json`.

See [`plugins/claude-code/README.md`](../plugins/claude-code/README.md) for the plugin layout and the release checklist.

## Codex plugin

The repository is also a Codex marketplace, `gabo-ai` ([`.agents/plugins/marketplace.json`](../.agents/plugins/marketplace.json)), with one plugin, `gabo`. It ships the same skills as the Claude Code plugin and two hooks that run `gabo check` around Codex's `apply_patch` edits in a gabo project. These steps are for the Codex CLI.

**With `gabo init`.** When `gabo.yaml` names `codex` in `runtimes.*`, `gabo init` adds `[marketplaces.gabo-ai]` and `[plugins."gabo@gabo-ai"]` to the project's `.codex/config.toml`, never to your global Codex config. Its `engine integration:` report then asks you to trust the project in Codex, so it loads `.codex/config.toml`, and to trust both gabo hooks in `/hooks`. If Codex does not list the gabo plugin after trust, the report tells you to run the two commands below. Commit `.codex/config.toml`. As the alternative, install the plugin by hand:

```sh
codex plugin marketplace add testeos-z/gabo-ai
codex plugin add gabo@gabo-ai
```

- **Trust the hooks.** Codex runs a plugin hook only after you trust it. In a Codex session, open `/hooks` and trust both gabo hooks: the `PreToolUse` hook denies a patch to a gabo file that breaks the stage gate (`gabo check --pre-write`), and the `PostToolUse` hook runs `gabo check` after the patch and returns its failures to Codex. A hook that changes in an update stays off until you trust it again. Both hooks do nothing outside a gabo project (no `.gabo/VERSION`) or when `gabo` is not on `PATH`. To turn them off, leave them untrusted.
- **Update.** Run `codex plugin marketplace upgrade gabo-ai`. Codex caches the plugin per version, so you get a new plugin when a CLI release bumps its version; then check `/hooks` again.
- **`gabo init` stays required.** The plugin does not configure a project and builds no agents. Run `gabo init` and the setup prompt with `runtimes.coder: codex`: the `gabo-runtime-codex` skill builds the agents as `.codex/agents/<id>.toml` and links the skills under `.agents/skills/`.

See [`plugins/codex/README.md`](../plugins/codex/README.md) for the plugin layout, how its skill and script copies stay equal to their sources, and the release checklist.

## Pi package

The Pi package `@gabo-ai/pi` ([`packages/pi/`](../packages/pi/)) ships the `gabo-pi` and `gabo-reviewer-config` skills and an extension that runs `gabo check --pre-write` at session start and before Pi's `write` and `edit` calls in a gabo project.

**With `gabo init`.** When `gabo.yaml` names `pi` in `runtimes.*`, a release build of `gabo init` adds the `packages` entry `npm:@gabo-ai/pi@<version>`, pinned to its own version, to the project's `.pi/settings.json`, never to your global Pi settings; a development build writes nothing and tells you to add the entry by hand. Its `engine integration:` report then asks you to trust the project in Pi, so it installs and loads `@gabo-ai/pi` from `.pi/settings.json`, and to install a subagent package. Commit `.pi/settings.json`. As the alternative, install the package by hand:

```sh
pi install npm:@gabo-ai/pi@<version>
```

Use the gabo CLI version as `<version>`. Before the package is on npm, install it from a checkout with `pi install /path/to/gabo-ai/packages/pi`. Check it with `pi list`.

- **`gabo init` and `gabo-runtime-pi` stay required.** The package itself writes no project file and builds no agents; with `runtimes.coder: pi`, `gabo-runtime-pi` builds them in `.pi/agents/` and links the skills under `.agents/skills/`.
- **It is not a subagent package.** gabo on Pi still needs one, such as gentle-pi; without it the extension warns at session start and blocks writes under `.pi/agents/`.
- **Coders run the reviewer script directly.** On every engine a coder validates the review request (`PR #<n> head <40-hex sha>`), runs the user-level reviewer script itself through its shell and acts on its `VERDICT` line; no agent relays the review. On Pi the coder is a gentle-pi subagent with no `subagent_*` tools, and the script is reached through the `skills/gabo-reviewer` link in the Pi agent home.
- **The user file needs a gentle-pi permission.** At session start the gabo assistant reads your global user file `~/.config/gabo/config.yaml` (`$XDG_CONFIG_HOME/gabo/config.yaml` when set), which is outside the project, so gentle-pi's permission gate asks before that read. Either approve that read once in an interactive session, or run unattended Pi waves in a gentle-pi permission mode that allows it (`/gentle:mode`, checked with gentle-pi 4.5.1). A read that is denied or waits for an approval nobody gives does not stop the session and does not run `gabo-setup`: the assistant reports `user config unreadable (<reason>): continuing without alias, language, tone and interaction level` and takes your identity from `developers` in `gabo.yaml` and `git config user.email`.
- **Unattended Pi waves need three Pi settings (known limits in 0.2.10).** A wave started from a Pi main session ran end to end on a server (probe P2a, [#414](https://github.com/testeos-z/gabo-ai/issues/414), Pi 1.5.0 with gentle-pi) only with these, which gabo does not set for you yet ([#463](https://github.com/testeos-z/gabo-ai/issues/463) tracks the follow-up):
  - **A long-lived session.** On Pi the wave launches coders as background subagents and waits for gentle-pi to wake it when each one finishes. `pi --print` exits when its first turn ends and kills those subagents, leaving the intent claimed. Run the wave in an interactive session or with `pi --mode rpc`.
  - **Access to the wave's worktrees and the reviewer.** gentle-pi keeps the main session inside the project root and the worktrees registered with it. The task worktrees (`worktree.dir`) and the user-level reviewer folder (`~/.local/share/gabo/skills/gabo-reviewer`) are outside it, so grant those paths in the session (or register each worktree) before starting the wave.
  - **Autonomous mode for `git push`.** gentle-pi asks before `git push` unless autonomous mode is on, and an unattended run denies the question, so coders stop at push. Set `GENTLE_PI_AUTONOMOUS_MODE=1` for the session, or `autonomousMode: true` in the project's `.pi/gentle-ai/runtime-guardrails.json`.

See [`packages/pi/README.md`](../packages/pi/README.md) for the package layout, coexistence rules and release pipeline, and [`packages/pi/VERIFY.md`](../packages/pi/VERIFY.md) for the manual verification run before each release.

## OpenCode

OpenCode needs no plugin install. The `gabo-runtime-opencode` skill copies the stage-gate plugin `.opencode/plugins/gabo-stage-gate.js` into the project, which runs `gabo check --pre-write` before writes. It builds the agents in `.opencode/agents/` and links the skills under `.agents/skills/`. `gabo init` writes the OpenCode config keys in the first existing of `opencode.json`, `opencode.jsonc`, `.opencode/opencode.json`, `.opencode/opencode.jsonc`, else in a new `.opencode/opencode.json`, comments kept: it sets only `default_agent`, and only when `runtimes.assistant` lists `opencode`; it creates no config file otherwise, never writes `experimental.subagent_depth` and leaves an existing value exactly as it is. It also reports whether the stage-gate plugin is in place.
