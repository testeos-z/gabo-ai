Evidence base (checked 2026-11-06 on `dev` at de617c2):

- `apps/cli/internal/slices/check/usecase.go` `checkAgents` (about lines 270 to 316): for each distinct runtime it requires a file named after every spec id in the runtime skill's `metadata.agent_dir`; it compares each file's `gabo-version:` line with the stamp only when the stamp is valid (`if !hasStamp { continue }`). `checkStamp` already fails a missing stamp (`✗ no stamp: run gabo init`), so the run fails, but the agent version lines are then not compared and not reported.
- `apps/cli/internal/slices/check/links.go` `checkLinks`: for each runtime with a `metadata.skill_dir`, one link `<skill_dir>/<name>` for the union of every spec agent's `skills`, plus the fixed-name slot links. It never reads an agent file's own skill list, so an agent that lost a skill passes while another agent keeps the link.
- `gabo-runtime-pi/SKILL.md` metadata declares `agent_dir: .pi/agents` and no `skill_dir`, although its build places `.pi/skills/` links; `checkLinks` therefore checks no skill link for Pi.
- Each runtime writes an agent's skills in its own place: Claude Code the frontmatter list `skills:`; Codex the line `Load these skills by name before work: <skills>.` inside `developer_instructions`; OpenCode and Pi the body line `Skills: before work read <dir>/<name>/SKILL.md for each of <skills>.` (runtime skills `gabo-runtime-claude` step 6, `gabo-runtime-codex` step 6, `gabo-runtime-opencode` step 6, `gabo-runtime-pi` "Agent files"). In each, the list is the spec `skills` in spec order, then the fixed-name links the template body names (`gabo-methodology`, `gabo-tasks`, `gabo-repository-host`, `gabo-memory`).
- Skill directories: Codex declares `skill_dir: .agents/skills`; OpenCode declares `.opencode/skills` but reads `.opencode/skills`, `.claude/skills` and `.agents/skills` (`gabo-runtime-opencode` evidence table, https://opencode.ai/docs/skills); Pi places links in `.pi/skills` but also reads `.agents/skills` ("Pi also supports the Agent Skills locations `~/.agents/skills/` and `.agents/skills/`", Pi 1.4.0 `docs/skills.md`; linked directories are followed, the same file is skipped, and on a name collision the first discovered skill is kept with a warning). Claude Code reads only `.claude/skills` (project, nested, `--add-dir` and plugin locations; no setting adds `.agents/skills`; https://code.claude.com/docs/en/skills.md). Owner correction, verbatim (2026-11-06): "ademas los agentes que usan .agents/skills/**.md debemos usarlo".
- The neutral agent spec `gabo-agent-templates/agents.yaml` gives each agent `id`, `role`, `skills`, `tools`, `launched_by` and `template`; nothing in `gabo check` reads `tools`, `launched_by` or the agent's declared name, and nothing refuses a project `gabo-reviewer` skill (TRD D20).

## 2. Design

The rules extend the existing `checkAgents` and `checkLinks` steps. What differs per engine (where an agent file keeps its skill list and its name) is declared by each runtime skill in its frontmatter, as `agent_dir` and `skill_dir` already are, so Go stays free of engine knowledge and a runtime skill written by `gabo-runtime-builder` can opt in.

| id | decision | options considered | choice | consequences |
|---|---|---|---|---|
| D1 | How `gabo check` finds an agent's skill list and name | A: Go parser per engine / B: runtime skill metadata, for example `agent_skills: frontmatter:skills` (Claude), `line:Load these skills by name before work:` (Codex), `line:Skills:` (OpenCode, Pi), and `agent_name: frontmatter:name` or `toml:name` | B, **Proposed (auto)**: keeps runtime knowledge in the runtime skills (TRD D24), same pattern as `agent_dir`; the exact key names and forms are fixed by the plan. | Each runtime skill gets two metadata keys; its build steps and the check read the same declaration. |
| D2 | Expected skill list | A: only spec `skills` / B: spec `skills` plus the fixed-name links the template body names | B, **Proposed (auto)**: that is what every runtime skill writes today. | The check reads the template from the project catalog copy, not from the binary. |
| D3 | Version state without a valid stamp | A: keep skipping / B: compare with the CLI version / C: check the line's presence and format and print one `not compared` failure | C, **Proposed (auto)**: no silent skip, no second guess of the expected version. | One extra line next to the stamp failure. |
| D4 | Tools, permissions and `launched_by` wiring | A: verify in 0.2.8 / B: defer | B, decided: deferred to a later intent (owner 2026-11-06 accepted the recommendation without objection). Each engine maps tools differently and some names depend on the session (Claude memory MCP servers, Pi "list only tools the session has"), and Codex has no tool list, so a check needs a per-engine tool map in each runtime skill first. | 0.2.8 checks presence, skills, name, version and reviewer isolation; tools and permissions go to a later intent. |
| D5 | Where the version bump to 0.2.8 lives | A: in each intent / B: one last task in this intent's plan, blocked by every intent 0009 task | B, **Proposed (auto)**: one bump, after both intents merge. | The plan carries cross-intent `0009/T<n>` dependencies. |
| D6 | Shared `.agents/skills` (owner correction 2026-11-06) | A: one skill directory per engine / B: every engine that reads `.agents/skills` uses it; Claude keeps `.claude/skills` | B, decided (owner, verbatim: "ademas los agentes que usan .agents/skills/**.md debemos usarlo" and "ok carpeta aparte"): Claude Code keeps a separate `.claude/skills` folder whose links point straight to `.gabo/skills`, because Claude Code cannot be told to read `.agents/skills` (https://code.claude.com/docs/en/skills.md). Duplicate discovery: Pi follows links and skips the same file, keeping the first on a name collision with a warning (Pi 1.4.0 `docs/skills.md`); OpenCode's handling of the same name in `.claude/skills` and `.agents/skills` is not documented, an assumption the plan verifies with a probe before the OpenCode task. | Fewer links; removal in a shared directory must consider every declared engine (S5). |
