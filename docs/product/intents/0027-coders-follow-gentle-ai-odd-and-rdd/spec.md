## 2. Design

The change keeps the existing homes of the coder rules. The methodology adapter (the slot, `gabo-methodology`) tells the coder how to build and how to run RDD. The coder skill and its agent template make the report and the preload binding. The cycle and the wave report carry the outcome to the owner. The reviewer side changes in the `gabo-reviewer` skill, whose scripts are installed at user level (TRD D20), not in the repository catalog. No new CLI command is added (PRD R31).

- the adapter `.claude/skills/gabo-methodology-gentle-ai/SKILL.md` (human merge, section 5);

- Hook 5, folder boundary: block the write.

Options, for every hook:

- **(b) Warn for the first wave, then block.** Tradeoff: one wave of data on false positives before enforcement; the bad action can happen in that wave.
- **(c) Warn only.** Tradeoff: keeps the wave moving; a push to main still happens, and the reviewer gate, not the hook, is the stop.

### 6.15 OpenCode, and any engine without the event (question 15)

- **(a) Warn and report.** The gap shows as `not run: <engine> has no <event>` in the outcome and in the wave report; the reviewer gate stays. Tradeoff: waves keep moving; the gap is visible, not closed.
- **(b) `gabo check` refuses a coder runtime that lacks a hook for a deny-class rule.** Tradeoff: the gap becomes a configuration error, and OpenCode coders stop until the event exists.
- **(c) Use the shell event where the probe proves it.** The repository's OpenCode 2.2.6 binary check shows that `execute.before` receives a `shell` call with `input.command`, and that a throw blocks the call (`apps/cli/internal/skills/gabo-runtime-opencode/SKILL.md:62`). The public page fetched lists no events, so the probe must confirm it. Tradeoff: closes the gap on OpenCode if the probe holds; rests on one binary version.
- **(d) No coder on that engine.** Tradeoff: the strongest guarantee; it drops an engine the PRD's full tier supports.

**Proposed (auto): (c) where the probe proves it, else (a).** Reason: it closes the gap where the event exists and keeps waves running with a visible gap where it does not. (b) and (d) cost a working engine.

### 6.16 Gabo missing or failing: fail open or fail closed (question 16)

- **(a) Fail open everywhere, with a warning.** This is today's behaviour for every gabo exit other than 0 or 1 (`gabo-pre-write.sh:43-44`), and for a missing gabo in OpenCode and Pi (their warnings; the Pi extension's `warnGaboUnavailable`). Tradeoff: a silent gabo failure lets a push to main through; the reviewer and branch protection are then the only stop.
- **(b) Fail open when gabo is absent; fail closed for the deny-class hooks 1, 2 and 5 when gabo runs and fails.** Tradeoff: a broken gabo stops a coder until it is fixed; a missing gabo still warns, so a machine without gabo is not blocked.
- **(c) Fail closed everywhere in a gabo project.** Tradeoff: the strongest rule; a machine without gabo cannot edit, which breaks the setup path.

**Proposed (auto): (b).** Reason: a missing gabo allows the call with a warning, as OpenCode and Pi do today, and the deny-class actions stop when gabo breaks.

### 6.17 How a human's release authorization is recorded (question 17, hook 2)

- **(a) A record the owner writes by hand, outside any coder worktree**, for example `~/.config/gabo/release-authorization.yaml`, with `version`, `tag`, `target_sha`, `authorized_by` and `date`. The gate matches all four; the shell guard denies any write to that path; the assistant mirrors the decision to memory. Tradeoff: local and simple, and it matches the release steps a human runs today (`plugins/claude-code/README.md:45-56`). An agent with shell access can write a file, so the record is proof only while its path stays denied to coders. That residual risk is not closed by this spec.
- **(b) A committed file under `.gabo/`, listed in `review.human_only_paths`.** The reviewer refuses a merge that changes it, and a human merges it. Tradeoff: reviewed and versioned, but one committed artifact per release; the reviewer, not the hook, is the stop for a forged record.
- **(c) A GitHub approval on the release step,** given by a person in GitHub and checked by no hook. Tradeoff: an approval an agent cannot forge (the playbook's approval "through branch protection", extraction); it needs repository settings the owner must set, and no such release step exists here.
- **(d) The memory record alone.** Excluded as a gate: no hook can read memory.

**Proposed (auto): (a), with the residual risk stated.** Reason: it is the only option a hook can check locally today, and the owner can move to (c) once the release path is automated. The owner's view on the residual risk is requested.

### 6.18 What "pasted output" means, and where gate 3 reads it (question 18)

- **(a) A fenced block per `review.checks` command in the hand-off text**, each starting with the command line as `gabo.yaml` lists it and ending with `exit: <n>`. The gate checks that every command is present with output and an `exit` line; it does not check that the command was run. Tradeoff: readable and checkable, but the text can be typed without running the command, so the proof stays the reviewer's run (S5).
- **(b) The output written to a log file under `mktemp -d`, named in the report,** which the gate reads by path. Tradeoff: the gate reads a file, but the coder controls the file and its path, so it proves no more than (a).
- **(c) No paste; the reviewer's run is the only evidence.** Tradeoff: removes the coder's evidence the playbook's builder step asks for ("Run all three before reporting any task complete, and paste the output", extraction).

**Proposed (auto): (a).** Reason: it is the form the playbook names, the gate can check its shape deterministically, and the reviewer's run keeps the truth.

### 6.19 How gate 4 reads a report that is chat output, not a file (question 19)

- **(a) The cycle reads the coder's outcome text before it writes the trace, and runs `gabo check` on it.** Works on all four engines, because the cycle is the orchestrator. Tradeoff: the check runs after the coder has ended, so a refused report costs one more coder run.
- **(b) The engine's hand-off event reads the last message.** Tradeoff: earlier, and it stops the coder in place. The payload is unverified: Claude Code's SubagentStop input is not known to carry the message, and Codex's Stop continues the turn and cannot reject it (evidence base). A continuation needs a cap so that it cannot loop.
- **(c) The coder writes the report to a `mktemp -d` file, and the cycle reads it.** Tradeoff: a file, but the coder writes it, so it is no stronger than (a).
- **(d) The coder posts the report as a tracker comment, and the gate reads the comment.** Tradeoff: visible to the owner, but a second report in the tracker, which D3 of this spec rejected.

**Proposed (auto): (a) enforces, and (b) is added where the probe shows the payload (D12).** Reason: (a) is engine-neutral and deterministic; (b) is earlier but rests on payloads not yet verified.

### 6.21 Folder boundary: how the task worktree is known, and which sessions are judged (question 21)

- **(a) The coder session's cwd, which the engine gives the layer, is the task worktree.** The rule checks that the write path lies under it and that `git worktree list` names it; the mktemp root is allowed; sessions with no coder role are not judged. Tradeoff: uses facts the engine already gives; depends on the engine starting the coder in its worktree, which the probe checks.

The coder's role comes from the engine's agent fact where the probe shows one (Claude Code documents `agent_type`). Where an engine shows none, the rule judges every session in the worktree: safe but noisy. The main checkout stays unjudged.

**Proposed (auto): (a), with the role fact from the probe.** Reason: no new file, and the engine already supplies the cwd. (b) is the fallback if the probe shows the cwd is not the worktree.
