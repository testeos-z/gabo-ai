Owner's configuration, approved, verbatim: "runtimes.assistant: a single engine or a non-empty list without duplicates, e.g. [claude, pi], every listed engine gets its own main-session entry and none removes another; runtimes.coder and runtimes.reviewer: an engine or "session" (run on the engine of the terminal running the wave; reviewer may also be a fixed engine such as pi so one engine reviews both teams). "session" valid only with assistant set; gabo check requires agents (and links, keys) of every listed engine plus any fixed reviewer engine; single values keep today behaviour."

Owner's coordination rule, verbatim: "a wave claims its intent before starting (a second session refuses a claimed intent and says which session has it), tasks are claimed as today, each wave keeps its own ledger and worktree namespace and cleans only its own resources."

Evidence base (checked 2026-11-06 on `dev` at e4b79be, gabo 0.2.10):

- **One engine per role.** `schemas/gabo.project.schema.json` `runtimes` (lines 44 to 52) gives `coder`, `reviewer` and `assistant` one `#/$defs/runtime` each; `apps/cli/internal/config/config.go` `Runtimes` (lines 72 to 75) holds one `Runtime` string per role, and `Validate` (lines 195 to 197) accepts only `claude`, `codex`, `pi`, `opencode`; `config/required.go` (lines 51 to 53) requires all three.
- **The engine set.** `gabo check` takes its engines from `runtimesOf` (`slices/check/links.go` line 332: the distinct values of the three keys); every engine rule uses it (agents, links, per-agent skills, reviewer isolation, leftover links, engine keys, OpenCode depth). `gabo init` reads the same three keys in `slices/initcmd/engines.go` `engineSet` and passes one assistant string to `engineconfig.Input.Assistant`.
- **One assistant engine.** `engineconfig/claude.go` `removesAgent` deletes `"agent": "gabo-assistant"` whenever the assistant is not `claude`; `engineconfig/opencode.go` (line 220) does the same for `default_agent`. `slices/check/mainsession.go` `checkMainSession` checks the entry of one engine and `checkStaleEntries` fails every other full-tier engine's entry with `✗ <file>: gabo assistant entry for <engine>, but runtimes.assistant is <value>`. Each runtime skill removes "the gabo entry of every other full-tier engine … that is not `runtimes.assistant`" (for example `gabo-runtime-pi` build step, line 109).
- **Waves.** `gabo-cycle` launches coders as in-process subagents, so they run on the engine of the session (TRD 2, Runtime inheritance); its reviewer gate reads `runtimes.reviewer` (Hard Rules, step 1). It claims tasks, not the intent: nothing marks an intent as taken, and `read unblocked` with the `intent` filter returns the same tasks to two sessions until one claims them. The ledger is already one Engram topic per wave (`gabo/ledger/<wave>`, wave id = intent id); the worktree path is not fixed by the skill.
- **Agent host.** `gabo-agent-host-local` starts a role with "the agent CLI of the role's runtime (`runtimes.coder` or `runtimes.assistant`: `claude` or `pi`)"; `gabo-direct-sessions-orca` and `gabo-agent-host-railway-orca` read `runtimes.coder` and `runtimes.reviewer` the same way.
- **Reviewer.** The user-level scripts read the engine from `REVIEWER_ENGINE` or `runtimes.reviewer` on the integration branch (`gabo-reviewer/scripts/common.sh` lines 190 and 442) and refuse any value other than the four engines (line 328); `declared_agent_dirs` (line 418) reads the three keys with `yaml_get`, which already reads a flow list `[a, b]`. `gabo-reviewer-placement-local` accepts only `PR #<n> head <sha>` and runs the scripts "with no extra arguments or environment".
- **Agent templates** have no slot that names the engine an agent was built for (`gabo-agent-templates`, slot table).

## 2. Design

The owner fixed the configuration; the design keeps one engine set for every reader, keeps `gabo init` the single writer of engine keys, and builds the coordination from the operations the slots already have.

| id | decision | options considered | choice | consequences |
|---|---|---|---|---|
| D1 | Shape of the keys | A: owner's shape (assistant engine or list; coder and reviewer engine or `session`) / B: a new `sessions:` block per engine | A, decided by the owner (config approved, quoted above). | Single values parse and behave as today; the Go `Runtimes` type and the schema gain the list and `session`. |
| D2 | One engine set | A: each reader computes its own / B: one rule (S2) used by `gabo init`, `gabo check` and the reviewer scripts | B, **Proposed (auto)**: a reader that differs leaves a failure another one cannot clear, the loop intent 0010 removed. | A Go helper in `config` or `engineconfig`; the scripts mirror it in shell, pinned by a test. |
| D3 | How an agent knows its session engine | A: a `{{engine}}` template slot filled by the runtime skill / B: the agent infers it from environment variables of the engine | A, **Proposed (auto)**: deterministic, written at build time and checkable by `gabo check` (S6); B depends on undocumented variables per engine. | Every agent file changes on the next rebuild; `gabo check` gains one rule (TRD 8.5). |
| D4 | Where the intent claim lives | A: comments on the intent issue through the existing `log progress` and `read one` operations / B: a new `claim intent` operation in the `tasks` contract / C: a lock in the memory slot | A, **Proposed (auto)**: no contract change, so no project adapter fails slot coverage in `gabo check`; the tracker is the shared state both sessions already read, and the earliest-comment rule settles a race without compare-and-set. B can come later if another tracker needs it. | The claim is visible on the intent issue; a claim survives a crash (open question 1). |
| D5 | Review engine under `session` | A: an explicit `engine` argument checked by the scripts against the integration branch config / B: an environment variable from the caller | A, **Proposed (auto)**: the placement skill forbids extra environment, and the scripts accept only an engine the owner listed on the integration branch, so a coder cannot pick an engine the owner did not configure (PRD R22). | The placement request gains an optional `engine <engine>`; the scripts gain one argument and its test. |
| D6 | Worktree namespace | A: `<repo-parent>/<repo-name>-worktrees/<wave>/<task>` / B: keep the path free | A, **Proposed (auto)**: a per-wave folder makes "cleans only its own resources" visible on disk and matches the CodeGraph placement rule of this repository. | `gabo-cycle` step 4 and `gabo-coder` name the path. |
| D7 | `gabo init` removal under a list | A: remove the gabo value of every full-tier engine not listed / B: never remove when a list is set | A, **Proposed (auto)**: keeps intent 0010 S4 and D2 ("remove the gabo value when the assistant engine changes") for engines dropped from the list, and the owner's "none removes another" for listed ones. | Intent 0010 S4 reads "not listed" instead of "not the assistant". |

## 6. Open questions

Owner rule, verbatim: "any floating question (a doubt the agents could not settle themselves after researching) must be passed up to the owner, not decided silently. Bring it with your proposed answer and its reasoning, one at a time." Each question below is passed up with a proposal and its reasoning; the plan treats each proposal as **Proposed (auto)** until the owner answers.

| # | question | status |
|---|---|---|
| 1 | Intent Q1: how is an intent claim released when its session ends without closing its wave (crash, closed terminal)? Proposal: no timeout; the claim holds until the holder's wave closes or resumes, or the owner tells any assistant to release it (the assistant posts `intent released by owner for session <id>`); the refusal line says so. Reasoning: no engine gives another session a reliable liveness signal, and a timeout that frees a live wave's intent lets two sessions run the same tasks, which is worse than a stuck claim that is visible on the issue and cleared with one sentence. | open, passed to the owner |
| 2 | Intent Q2: when `runtimes.coder` is a fixed engine other than the session's engine, what runs the coders? Proposal: today's behaviour, in-process coders on the session engine, plus one wave-report line `coders ran on <session engine> (runtimes.coder is <engine>; subagents inherit the session engine)`. Reasoning: the owner said "single values keep today behaviour", subagents cannot change engine (TRD 2), and starting coders as separate processes through `agent_host` would be a new launch path outside this brief; `session` already covers the owner's need. Alternative: refuse the wave in that case, which breaks today's single-value projects. | answered by the owner on 2026-11-06, verbatim: "si" (resolver: owner): the proposal, in-process coders on the session engine plus the wave-report line |
| 3 | Intent Q3: does `parallelism` bound the coders of each wave or of the whole project when several waves run at once? Proposal: each wave, as today. Reasoning: each team runs on its own subscription, which is the point of the owner's need, and a project-wide bound would need a shared counter between sessions that no slot offers; the owner can lower `parallelism` if the machine is the limit. | answered by the owner on 2026-11-06, verbatim: "si acepto su propuesta" (resolver: owner): each wave, as today; no project-wide counter |
