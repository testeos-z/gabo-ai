## Steps

1. **Keys and runner, one chain.** T1 (eval keys in `gabo.yaml`, loader, validation, schemas: S2, S4, S8, S9 values; D4, D5), then T2 (set format, validation, secret refusal, the runner skill), then T3 (engine execution of one run in a scratch copy: S4). T4 (method evidence, S5) and T5 (cap, S8) both follow T3 and are disjoint scripts. T6 (report and baseline, S6, S7) follows both; T7 (notice, S9) follows T6.
2. **Merge hold.** T8 (S10, the merge step) follows T7 for the marker contract and 0027/T10, because 0027 pins the merge gate of `merge-head.sh` as unchanged in its comment-order task. Reason: one owner per shared file at a time.
3. **Assistant rules, one chain.** T9 (trigger rule and path list, S3) follows T2. T13 (incident, two-times and review-finding rules: S13, S15, S17, S18) follows T9 and T12, since both edit `gabo-assistant`. T14 (incident line of the trace and the report) follows T13 and 0027/T5, because 0027 edits the same `gabo-cycle` and `gabo-wave-report` steps. T10 (the hook entry of S3's path list) follows T9 and the four relay tasks of 0028 (T10 to T13), which create the hook files.
4. **Instruction file, template and lessons, independent.** T11 (`AGENTS.md` blocks, S16, S17), T12 (`docs/product/LESSONS.md`, S14, D7, D8) start with no dependency. T15 (template and setup offer, S19) follows T11 so the template copies the block shape that the repository's own file uses.
5. **First set and baseline.** T16 proposes the first eval tasks from finished work and the first baseline to the owner; nothing runs until the owner accepts them (S1, S6). It follows T6.
6. **Probe.** T17 runs one configuration PR below the threshold on the owner's machine and checks the notice, the dedupe and the hold. It needs the owner's threshold and cap values and the `gabo init` refresh of the user-level scripts.

The spec's end-to-end acceptance is checked by T17, not by any single task.
